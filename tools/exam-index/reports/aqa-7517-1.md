# AQA 7517 Paper 1 — examiner's report notes

Paraphrased from AQA's *Report on the Examination* (saved in your folder by
`tools/fetch_reports.py`), in our own words, citing series and question.
Section A's marks and leaves come from the index; Sections B–D (the
program and the Skeleton Program, refinement R4) are not indexed, so they
are cited by question only.

Only June 2022 was reachable from AQA's file store.

---

## June 2022 — on the day

- Use the Preliminary Material from September; test the Skeleton Program on
  the exam machines beforehand.
- **A screen capture not produced by your own running code scores
  nothing.** Spend that time making the code work.
- Paste code as text into the EAD; screenshots of code get cropped or are
  unreadable, and cropped lines lose marks.
- Crop test evidence carefully: an over-cropped capture lost the testing
  mark on working code (Q12.2).
- Attempt the long modification questions: the first marks are for simple
  parts (declaring and initialising a variable in the right place).
  Over 15% skipped Q13 and gave those marks away.

## Section A (theory)

### Q02.1 (4) · 4.2.2.1 removing from a circular queue
- Poor. Traps: removing from the rear; shuffling items "up one" (that is a
  linear queue); forgetting to **check for empty first**.
- Marks: check empty; take the item at front; move front on by one,
  wrapping with MOD; reduce the size count.

### Q02.2 (3) · 4.2.1.4 static vs dynamic structures
- Few gave three. Beyond fixed size: memory allocated at compile time vs
  run time, possible wasted space vs overhead of pointers, heap use.

### Q02.5 (2) · 4.2.3.1 reversing a queue with a stack
- Common omission: putting the items **back into the queue** after
  popping them from the stack.

### Q03.1–Q03.3 (1+1+2) · 4.4.1.1 logic puzzle
- "It's a contradiction" alone scored nothing — say which statements
  conflict and why.
- Trap: discarding a statement because it says the same as another.

### Q04.3 (2) · 4.2.4.1 short algorithm trace
- Only about 20% correct. Traps: returning several values; extra values
  for the counter. Follow the code exactly, line by line.

### Q04.5 (6) · 4.3.1.1 + 4.1.1.16 recursive traversal trace
- About 10% full marks, though the early rows earned partial credit.
  Keep the call stack written down as you go.

### Q04.6–Q04.8 (1+1+1) · 4.3.1.1 what the algorithm is
- Recognising depth-first was easier than the purpose questions; some
  got these without a correct trace.

## Section B (write a program)

### Q05 · reverse the order of the vowels in a string
- About a third fully working; finding the vowels alone got about half.
- Traps: loop stopping before the **last character**; wrong combination
  of vowel conditions; failing with 0 or 1 vowels; indexing past the end.
- Working shapes: collect vowels in a list, reverse it, put them back;
  or two pointers from each end; a stack or recursion also worked.

## Section C (questions on the Skeleton Program)

### Q06.3 · protected
- Often described private instead. Protected: visible in the class **and
  its subclasses**. Not about who may edit the code.

### Q06.4 · overriding
- Vague answers lost the mark. Tie it to **inheritance**: a subclass
  redefines a method it inherited, with the same signature.

### Q07.2 · why not a set
- "Values must be unique" is true but irrelevant. A set has **no order**,
  and a deck needs one.

### Q07.3–Q07.4 · a hash table for the cards
- Most gave "the hash gives the storage location". Fewer gave collision
  handling, or hashing the card number because it is unique. Suitability:
  direct access in constant time.

### Q08.2–Q08.3 · identifiers and stack frames
- An identifier must clearly be about the thing asked (the hand).
- A stack-frame answer must name what **this** subroutine's frame holds,
  not the generic list.

### Q10 · a regular expression
- Most couldn't write it accurately; many didn't use `|` for alternation.

## Section D (modify the Skeleton Program)

### Q11 · input validation
- Over half full marks. Traps: combining two conditions wrongly; no error
  message. Recursive retries often ignored the returned value, which
  broke the game afterwards.

### Q12 · count tool cards in the deck
- About 40% full marks. Traps: counting one tool type twice; wrong
  compound conditions; a loop missing the last card.

### Q13 · a one-use blasting cap
- About 15% full marks. Traps: initialising the "used" flag where it
  **resets every turn**; an off-by-one in the position check (the user's
  position needs −1 for the index).
- The test must show everything asked, including the second attempt.

### Q14 · a trap card subclass
- Very few full marks. Traps: inheriting from Card instead of
  DifficultyCard; code that can pick an unmet challenge or change several;
  missing a change in GetCardFromDeck.
- Working shapes: a list of the met challenges' indexes, or check that one
  exists and draw at random until a met one comes up.
